PROJECT
A deployed, AI-native MVP for first-time mutual fund SIP investors (Groww case study): "SIP Explainer". It explains in plain English why a user's SIP value can sit below their invested amount even when the fund itself is only slightly down. Five screens, matching the images in /design (Home, My SIPs, SIP Overview, My Investment Analysis, Fund History): match layout, colours and copy as closely as practical. Flow: Home -> My SIPs -> SIP Overview -> My Investment Analysis <-> Fund History (toggle).

WHERE THE AI LIVES
- Live AI exists ONLY on My Investment Analysis: (1) the generated Smart Digest and (2) the inline "Ask about your SIP" card. Both go through the eval gate described below.
- Every other screen, including Fund History, is static (pre-written text and sample data, no AI calls). The Fund History "Ask about this fund" card is a disabled preview with a grey "Coming soon" pill. No "AI explanation" tag or "Numbers verified" badge anywhere on Fund History.

HARD CONSTRAINTS (enforced in code, not only in prompts)
- Never recommend specific funds or stocks. No investment advice of any kind (no should / buy / sell / hold / switch / stop / continue recommendations). No fear, FOMO or urgency wording. No predictions of future prices or returns. No fund ratings (no CRISIL badge).
- "Educational explanation, not investment advice." is visible on every analysis screen, in the Ask card and in the footer.
- Red is used only on loss figures themselves. Strips, buttons and charts use neutral blue and grey.

STACK AND PERFORMANCE
- Python + Streamlit with custom CSS, mobile width about 420px centred, no Streamlit chrome visible. Single-file router using st.session_state["screen"] with a custom fixed bottom navigation (Home, My SIPs only). Back arrows return to the previous screen. Avoid full-page flicker: run the Ask card inside st.fragment so asking a question does not rerun the whole page, cache computed values with st.cache_data, and generate the Smart Digest once per scenario and cache it for the session (show a skeleton while it loads, never a different screen).
- Groq API with a strong instruct model (check Groq's current model list and pick a Llama 3.3 70B-class model). Key in Streamlit secrets or .env, never in code or chat.
- Files: app.py, core/compute.py, core/llm.py, core/gate.py, core/templates.py, core/static_data.py, golden_set.json, eval.py, eval_results.json, logs/, README.md, requirements.txt. Deploy to Streamlit Community Cloud.

CORE PRINCIPLE: NUMBERS COME FROM CODE, THE AI ONLY WRITES WORDS
1. core/compute.py takes monthly_amount and a list of instalment NAVs (the last NAV is today's NAV) and returns: invested, units_total, units_per_instalment, avg_cost, nav_start, nav_now, value, diff, return_pct, fund_return_pct, month_end_values and month_end_invested (for charts), gap per month, month with most units, highest and lowest instalment NAV, and a relation flag (sip_lower / sip_higher / equal comparing return_pct with fund_return_pct). Format with Indian digit grouping and the rupee sign; percentages to 2 decimals; units to 2 decimals.
2. The LLM only receives these values as JSON and writes using placeholders like {invested}, {value}, {diff}, {return_pct}, {fund_return_pct}, {avg_cost}, {nav_now}, {nav_start}, {units_total}, {n_instalments}, {monthly}, {units_prev}, {units_last}, {nav_last}, {nav_low_range}, {nav_high_range}. Code fills placeholders after validation. Any digit written outside a placeholder is a validation failure.

AI FEATURE: ONE LLM CALL PER QUESTION
- Input: computed JSON, the question, a short glossary (NAV, units, average cost, unrealised vs realised, XIRR, rupee-cost averaging, point-to-point return).
- Output: strict JSON {"route": "answer | decline_advice | decline_prediction | redirect_offtopic | not_sure", "answer": "..."}. Temperature 0.2.
- System prompt rules: plain English at about grade 8 (simple Hinglish in Roman script if the question is in Hinglish); max 110 words; calm, neutral tone; only placeholders for numbers; state the direction of the difference correctly (gain, loss or none) and whether the SIP did better or worse than the fund over the same period and why (units bought at different NAVs); say a difference only becomes a gain or loss when units are sold when relevant; never say what the user should do; never mention any other fund or stock; no causes of market moves; no predictions.
- Only route "answer" uses generated text. For every other route IGNORE the model's text and return a fixed template from core/templates.py filled with computed values. Add a regex backstop on the question for obvious advice and prediction phrases (should I, stop my SIP, sell, buy, which fund, better than, will it recover, will I lose); if it fires, force the decline template regardless of the router.
- The Smart Digest uses the same pipeline with a fixed "explain my SIP in simple words" request.

EVAL GATE (every generated answer, in order)
1. JSON parses and the route is allowed.
2. Digit check: no digits outside placeholders; every placeholder is a known key.
3. After filling: every number in the final text belongs to the allowed set from compute().
4. Advice phrases (blocklist: "you should", "i recommend", "buy", "sell", "switch to", "redeem", "stop your sip", "continue your sip", "better fund", "best fund") must not appear.
5. Fear/urgency terms (blocklist: "panic", "crash", "danger", "hurry", "last chance", "don't miss", "losing everything", "wipe out", "disaster", "alarming") must not appear.
6. Readability: average sentence length at most 22 words, answer at most 110 words.
7. For explanation questions the stated relation (SIP lower, higher or equal to the fund) must match compute()'s relation flag, using a strict yes/no LLM judge at temperature 0 (labelled as an LLM judge in the README).
On failure retry once with the failure reason added. If it fails again, show the fallback standard explanation. Never show an unverified answer.
